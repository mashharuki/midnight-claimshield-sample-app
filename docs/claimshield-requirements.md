# ClaimShield 要件定義（MVP）

> ステータス: ドラフト
>
> 対象リポジトリ: `midnight-claimshield-sample-app`
>
> 本書は「何を利用者に提供するか」を定義する。Compact 回路、SDK プロバイダー、データ型などの実装詳細は設計フェーズで決定する。

## 概要

ClaimShield は、従業員・会員などの利用者が、**支出額・店舗名・レシート内容・本人のウォレットアドレスを公開せず**、福利厚生または経費ポリシーへの適合をゼロ知識証明で示す dApp である。

初期の対象ユースケースは「ランチ補助」のような**固定給付の申請**とする。利用者は、レシートの支出額が指定範囲内であること、および同じレシートで申請していないことを証明する。組織は、個別の支出明細を見ずに、適格な申請件数と承認状態だけを確認できる。

管理者による承認は、申請者が dApp 外で任意に提出した資料を確認済みであることを記録する操作であり、ClaimShield 自身は資料を保存・配布・真偽判定しない。承認済みの申請者は、同じ秘密入力の保持者であることを ZK で再証明して、一度だけ「引換済み」へ遷移できる。

### 登場人物

- **ポリシー管理者**: 申請ポリシーを作成し、受付開始・終了、承認、取消を行う組織側の利用者。
- **申請者**: 秘密情報を端末に保持し、適格性を証明して申請する利用者。
- **閲覧者**: 公開されているポリシーの条件、申請件数、申請ステータスを参照する利用者。

### プライバシー境界

| 公開する情報 | 秘匿する情報 |
| --- | --- |
| ポリシー名、対象カテゴリ、申請期間、最小・最大支出額、固定給付額、受付状態 | 申請者の実アドレス、実際の支出額、店舗名、レシート画像・本文、レシートハッシュの原像、salt |
| 申請のコミットメント、使用済みレシートを表す nullifier、申請数、承認／取消状態 | 申請に用いた秘密鍵、申請者と公開上の申請キーとの対応 |

ClaimShield は「UI 上で隠すだけ」のアプリではない。申請時には、秘密値から作ったコミットメントとゼロ知識証明を用い、ポリシー適合とレシートの一回利用をコントラクトが強制する。

公開上の申請キーは匿名化のための疑似 ID であり、同じコントラクト内における複数の操作はリンク可能である。ClaimShield は完全な匿名性ではなく、申請内容および実ウォレットアドレスの選択的秘匿を提供する。

### MVP の対象外

- NIGHT、tNIGHT、法定通貨などの送金・エスクロー・自動払戻し
- レシート画像のオンチェーン保存、OCR、外部会計サービス連携
- 審査資料の暗号化配布、端末間同期、秘密値の紛失後の復旧
- 実在企業の在籍確認、KYC、複数組織間で共有する資格証明
- 不正利用の最終的な事実認定。ClaimShield はポリシー適合と重複防止を証明するものであり、レシート内容の真偽を保証しない

## このアプリのゴール（デモで行うこと）

デモでは、管理者 1 名と申請者 2 名が同一ポリシーを使い、以下を一貫して見せる。

1. 管理者が「ランチ補助・支出額 800〜1,500 ポイント・給付 500 ポイント・受付中」というポリシーを作成する。
2. 申請者 A が、支出額・店舗・レシート識別子をローカル入力し、適格性を証明して申請する。
3. 画面上および公開状態には、A の実額・店舗・レシート内容が一切表示されず、申請コミットメントと適格ステータスだけが表示される。
4. A が同じレシート識別子で再申請すると、二重申請として失敗する。
5. 申請者 B が範囲外の支出額で申請すると、ポリシー違反として失敗する。
6. 管理者が有効な申請を承認し、公開ダッシュボードで承認数と固定給付予定額を確認する。
7. 申請者 A が同じ秘密入力を再提示して、一度だけ引換済みへ遷移する。金銭の送付は行わない。
8. 申請者 A が必要なら、ローカルに保持する明細を選択的に表示できることを説明する。MVP では、その明細の共有先・保管は利用者の端末に限定する。

デモの成功条件は、第三者が公開状態だけを見ても「誰が、どの店で、いくら支払ったか」を復元できず、かつ適格性・一回性・承認状態は検証できることである。

## 実装する機能

### 1. ポリシー管理

- 管理者は、ポリシー名、対象カテゴリ、開始・終了時刻、支出額の下限・上限、固定給付額を指定してポリシーを作成できる。
- 管理者は、受付中のポリシーを終了できる。
- 管理者は、適格に提出された申請を承認または取消できる。
- 閲覧者は、ポリシー条件、状態、申請数、承認数、固定給付予定総額を確認できる。

#### 受入要件

##### Requirement 1. ポリシーの作成と公開

1. When 管理者が有効なポリシー条件を送信したとき, the ClaimShield shall 新しい受付中ポリシーを作成し、公開条件と管理者を記録する。
2. If 開始時刻が終了時刻以降、下限が上限を超過、または固定給付額が 0 のとき, the ClaimShield shall ポリシーの作成を拒否し、条件が無効であることを表示する。
3. When 閲覧者がポリシーを開いたとき, the ClaimShield shall 公開条件、受付状態、申請数、承認数、固定給付予定総額を表示する。

##### Requirement 2. ポリシーの終了と申請判断

1. When 管理者が受付中ポリシーを終了したとき, the ClaimShield shall 以後の申請を受け付けない状態に変更する。
2. While ポリシーが終了済みであるとき, the ClaimShield shall 新規申請を拒否する。
3. When 管理者が適格な未判断申請を承認したとき, the ClaimShield shall 申請を承認済みに変更し、承認数および固定給付予定総額を更新する。
4. When 管理者が適格な未判断申請を取り消したとき, the ClaimShield shall 申請を取消済みに変更し、取消理由の入力欄を表示する。
5. If 管理者以外がポリシー終了、承認、または取消を試みたとき, the ClaimShield shall 操作を拒否する。
6. When 管理者が承認または取消を実行するとき, the ClaimShield shall 審査資料は dApp 外で確認済みであることを表示する。

### 2. 秘匿申請と適格性証明

- 申請者は、支出額、店舗名、レシート識別子を端末上で入力する。
- 申請者は、値がポリシーの対象期間および支出額範囲に収まることを、値そのものを公開せずに証明して申請する。
- 申請の秘密値、salt、申請者秘密鍵は申請者のローカル private state に保存する。
- 申請者は、自分の申請についてのみ、ローカルに保存された明細と状態を閲覧できる。

#### 受入要件

##### Requirement 3. 秘匿値の作成と保管

1. When 申請者が申請の入力を開始したとき, the ClaimShield shall 支出額、店舗名、レシート識別子を公開画面や公開状態に表示しない。
2. When 申請者が適格な明細を申請したとき, the ClaimShield shall 明細のコミットメントと適格性の証明を記録し、秘密値を申請者のローカル状態に保存する。
3. When 申請者が自分の申請詳細を開いたとき, the ClaimShield shall その端末に保存された秘密値と公開申請状態を対応付けて表示する。
4. If 申請者のローカル秘密値が利用できないとき, the ClaimShield shall その申請を再証明または詳細表示できないことと、復元にはバックアップが必要であることを表示する。

##### Requirement 4. 支出額範囲のゼロ知識検証

1. When 申請者が申請を送信したとき, the ClaimShield shall 実際の支出額を公開せずに、支出額がポリシーの下限以上かつ上限以下である場合にだけ申請を受理する。
2. If 支出額がポリシー範囲外のとき, the ClaimShield shall 申請を拒否し、範囲外であることを申請者に表示する。
3. If 申請に使う秘密値が提出済みコミットメントと一致しないとき, the ClaimShield shall 申請を拒否する。

### 3. 重複申請の防止

- 同一ポリシーに対し、同一レシート識別子を二度使えないようにする。
- 重複判定に必要な nullifier は公開してよいが、そこからレシート識別子を推測できないようにする。
- 別ポリシーへの申請は、ポリシーごとに独立して扱う。

#### 受入要件

##### Requirement 5. レシートの一回利用

1. When 申請者が未使用レシートで申請したとき, the ClaimShield shall そのポリシー内で一意なレシート nullifier を記録する。
2. If 同一ポリシー内で記録済みのレシート nullifier を使って申請したとき, the ClaimShield shall 二重申請として拒否する。
3. When 異なるポリシーに同じレシート識別子で申請したとき, the ClaimShield shall 各ポリシーのルールに従って独立に判定する。

### 4. ウォレット、トランザクション、エラーの体験

- 利用者は Midnight 対応ウォレットを接続して、ポリシー操作または申請を行う。
- 証明生成・署名・送信・確定の各段階が、申請者に分かる状態で表示される。
- 失敗時に秘密値や秘密鍵をエラー表示・ログ・URL に含めない。

#### 受入要件

##### Requirement 6. ウォレット接続と操作状態

1. When 利用者がウォレット未接続で書き込み操作を選択したとき, the ClaimShield shall 接続を促し、接続完了まで操作を実行しない。
2. While 証明生成、署名、送信、または確定を待っているとき, the ClaimShield shall 現在の段階を表示し、同一操作の重複送信を防止する。
3. If トランザクションまたは証明生成に失敗したとき, the ClaimShield shall 再試行可能な説明を表示し、秘密値を表示しない。

### 5. 一回限りの引換

- 承認済みの申請者は、提出時と同一の秘密入力の保持者であることを証明して、申請を一度だけ引換済みにできる。
- 引換は給付の受領資格を記録する状態変更であり、MVP で資産を送付しない。

#### 受入要件

##### Requirement 7. 承認済み申請の引換

1. When 承認済み申請者が提出時と一致する秘密入力を再提示したとき, the ClaimShield shall 申請を引換済みに変更する。
2. If 却下済み、未承認、または引換済みの申請を引換しようとしたとき, the ClaimShield shall 操作を拒否する。
3. If 再提示した秘密入力が申請コミットメントと一致しないとき, the ClaimShield shall 操作を拒否する。
4. When 申請が引換済みになったとき, the ClaimShield shall 資産送付を行わず、一回限りの資格記録が完了したことを表示する。

### 6. デモデータと検証

- 開発環境では、ランチ補助ポリシーと 2 件以上の申請シナリオを再現できる。
- 少なくとも、有効申請、範囲外申請、重複申請、承認、取消の挙動を自動テストで検証する。
- ソースコードからコントラクトとアプリをビルドできる。

#### 受入要件

##### Requirement 8. 再現可能なデモ

1. When 開発者が README の手順を完了したとき, the ClaimShield shall 新規ポリシー作成から承認までのデモを実行可能にする。
2. When 自動テストを実行したとき, the ClaimShield shall 有効申請、範囲外、重複、承認、取消、引換、引換の重複実行の各シナリオを検証する。
3. When 開発者がクリーンな環境でビルドしたとき, the ClaimShield shall 事前生成済みアーティファクトだけに依存せず、Compact ソースを含むプロジェクトからビルドできる。

## UI/UX・画面のイメージ

### 1. ホーム／ポリシー一覧

- 目的: 利用者が利用可能なポリシーと自分の次の操作を理解する。
- 表示: ウォレット接続、ネットワーク切替、ポリシーカード、受付状態、支出額範囲、固定給付額、申請数、承認数。
- 行動: 管理者は「ポリシーを作成」、申請者は「申請する」、閲覧者は「詳細を見る」を選ぶ。

### 2. ポリシー詳細

- 目的: 公開条件とプライバシー境界を明確にする。
- 表示: 条件、期間、現在の状態、申請・承認集計、管理者操作。
- 重要な案内: 「支出額・店舗・レシートは端末だけに保存され、チェーンへ公開されない」「申請の一回性だけを証明する」を常時表示する。

### 3. 秘匿申請ウィザード

- ステップ 1: 支出額、店舗名、レシート識別子を入力する。各入力欄には「ローカルにのみ保存」と表示する。
- ステップ 2: 公開される情報（コミットメント、nullifier、申請状態）と秘匿される情報を対比表示する。
- ステップ 3: 証明生成、ウォレット署名、送信、確定を順に表示する。
- 完了: 成功した申請の状態と、秘密値を失うと再証明できない注意を表示する。

### 4. 自分の申請一覧

- 目的: 申請者だけが、ローカル明細とオンチェーン状態を照合できるようにする。
- 表示: 自分の店舗名・支出額・申請日時・公開状態・承認状態。ローカルデータが見つからない場合は、秘密値を表示せず復元案内を出す。

### 5. 管理画面

- 目的: 個人の明細を見ないまま申請状態を判断できることを示す。
- 表示: 申請コミットメント、受付日時、適格性、承認／取消操作、集計。支出額、店舗、レシート本文、申請者ウォレットアドレスは表示しない。
- 重要な案内: 承認・取消の根拠となる資料確認は dApp 外の運用であり、この画面は確認結果だけを記録する。

### UX 原則

- 秘匿データと公開データを色・アイコン・説明文で明確に分離する。
- 証明中・ウォレット承認待ち・確定待ちを一つの曖昧なローディング表示にまとめない。
- 秘密値の紛失リスクを申請前と申請完了後の両方で伝える。
- 日本語・英語の表示を提供し、専門用語には短い補足を付ける。

## 技術スタック & フォルダ構成案

既存の Bun ワークスペース構成を維持する。新しいトップレベルパッケージ、別フレームワーク、別バックエンドは MVP では追加しない。`pkgs/` 以下の責務分割、既存のウォレット・ネットワーク基盤、CLI 運用を再利用する。予測市場由来のドメイン名を ClaimShield 名へ変更する場合は、コンパイル出力・公開 ZK 資産・import・ルート scripts を一括で更新し、生成物を手編集しない。

### 技術スタック

| 領域 | 利用する既存技術 | ClaimShield での役割 |
| --- | --- | --- |
| モノレポ | Bun workspace | ルートからビルド、テスト、開発サーバーを実行する |
| コントラクト | Compact / Compact Standard Library | コミットメント、nullifier、受付状態、承認状態、ポリシー条件を検証する |
| Midnight 連携 | Midnight.js 4.0.4、compact-js 2.5.0、compact-runtime 0.15.0 | 証明生成、コントラクト呼び出し、公開状態の取得を行う |
| ウォレット | DApp Connector API / Lace 対応の既存接続層 | 接続、署名、手数料処理を行う |
| フロントエンド | React 19、Vite、TypeScript、Tailwind CSS、Radix UI | 申請ウィザード、ポリシー画面、状態表示を提供する |
| テスト | Vitest | Compact シミュレータとフロントエンドロジックを検証する |
| 多言語 | i18next / react-i18next | 日本語・英語の画面文言を管理する |

### 既存実装から再利用するもの

- `pkgs/app/src/contexts/` のウォレット接続・ネットワーク切替

### 後続フェーズで決定する設計事項

- コミットメントと nullifier の正確な preimage、domain separation、鍵導出規則
- private state のバックアップ／復元形式
- 承認者への選択的開示を MVP 後に追加する際の暗号化・同意フロー
- 固定給付から実費精算や資産決済へ拡張する際の会計・トークン設計

## 次の承認ポイント

この要件で合意した後、設計フェーズで公開 ledger、private state、witness、各 circuit、画面間のデータフローを確定する。特に「固定給付で開始し、資産決済は行わない」という境界を、実装開始前に固定する。
